# Security Design

## 概要

HoneyWatch は攻撃者に意図的にサービスをさらすため、通常のアプリケーション以上にセキュリティ設計が重要です。本ドキュメントでは、設計上のセキュリティ判断を記載します。

## 脅威モデル

| 脅威 | 対策 |
|------|------|
| Honeypot 経由で管理系に侵入 | ネットワーク分離（Honeypot → Redis のみ通信可能、DB/API に直接到達不可） |
| 攻撃者が Honeypot のプロセスを掌握 | 最小権限（非 root ユーザー）、コンテナ隔離 |
| DB 内のパスワードが漏洩 | 平文保存のリスクを認識した上で分析価値を優先。DB アクセス制御 + バックアップ暗号化で保護 |
| 管理 API への不正アクセス | Basic Auth + ポート公開を 127.0.0.1 限定 + 本番では IP 制限 |
| ログ内の個人情報（IP）の漏洩 | Dashboard は認証必須、DB は外部非公開 |

## 最小権限の原則

### コンテナ実行ユーザー

```dockerfile
RUN groupadd -r honeywatch && useradd -r -g honeywatch honeywatch
USER honeywatch
```

- Honeypot / API / Worker すべて非 root で実行
- コンテナ内でホスト側のファイルシステムにアクセス不可

### Honeypot の権限範囲

Honeypot コンテナができることは:
- 指定ポートで TCP 接続を受ける
- Redis Stream にイベントを XADD する

Honeypot コンテナができないことは:
- PostgreSQL に直接アクセス
- 他コンテナのファイルシステムにアクセス
- ホストネットワークへのアクセス

## ネットワーク分離

### Docker ネットワーク

| ネットワーク | 参加コンテナ | 用途 |
|------------|------------|------|
| honeypot_net | Honeypot | 外部からの攻撃トラフィック受信 |
| internal_net | 全コンテナ | 内部通信（Redis, DB, API） |

### ポート公開ポリシー

| サービス | バインドアドレス（ホスト:コンテナ） | 理由 |
|---------|----------------|------|
| SSH Honeypot | `0.0.0.0:22` → コンテナ 2222 | 攻撃者に公開する必要がある |
| HTTP Honeypot | `0.0.0.0:80` / `0.0.0.0:8080` → コンテナ 8080 | 攻撃者に公開する必要がある（80 で無差別 Web スキャンも観測） |
| 管理 SSH | `0.0.0.0:2200`（SG で自分の IP のみ許可） | ホスト管理用 |
| API | `127.0.0.1:8000` | 管理者のみアクセス |
| Dashboard | `127.0.0.1:3000` | 管理者のみアクセス |
| PostgreSQL | `127.0.0.1:5432` | 外部非公開（内部のみ） |
| Redis | `127.0.0.1:6379` | 外部非公開（内部のみ） |

### AWS デプロイ時の Security Group

```
Inbound:
  # 攻撃観測用（全開放）
  - 22/tcp    : 0.0.0.0/0        (SSH Honeypot)
  - 80/tcp    : 0.0.0.0/0        (HTTP Honeypot: 無差別 Web スキャン観測)
  - 8080/tcp  : 0.0.0.0/0        (HTTP Honeypot)
  # 管理用（自分の IP のみ許可）
  - 2200/tcp  : 自分の IP/32     (管理 SSH)
  - 8000/tcp  : 自分の IP/32     (API)
  - 3000/tcp  : 自分の IP/32     (Dashboard)
  # 外部非公開（127.0.0.1 バインド。SG では公開しない）
  # - 5432 (PostgreSQL) / 6379 (Redis) は Inbound に追加しない

Outbound:
  - All traffic : 0.0.0.0/0
```

> 上記 Outbound の全許可は本ドキュメント初版の値。現状の実態に即した推奨ルールは次の「アウトバウンド（Egress）設計」を正とする。

## アウトバウンド（Egress）設計

### 方針（現状フィット: 全閉じ寄り）

HoneyWatch は攻撃者を意図的に招き入れる Honeypot であるため、**アウトバウンドは「全許可（デフォルト）」のままにしない**。侵害時の踏み台化・情報持ち出しの経路を最小化するため、最小権限で設計する。

**現状のコード実態を正とする。** アプリ本体（Honeypot / Worker / API / Dashboard / DB / Redis）には、収集データを外部へ送信する機能が**まだ一切実装されていない**（通知・AI 分析・GeoIP 更新はいずれも Phase 3-4 の未実装機能。コードベースに外向き HTTP クライアント送信は存在しない）。したがって現時点で「アプリ用途のアウトバウンド」を許可する理由はなく、ほぼ全閉じにできる。

完全ゼロにはせず、ホスト（EC2）運用に最低限必要なものだけを常時許可する。それ以外（HTTPS=443）は**普段は閉じ、OS 更新や Docker イメージ取得などの作業時だけ一時的に開放**する運用とする。

重要な前提として、**Honeypot コンテナ自身は外向き通信を必要としない**（攻撃を受信して Redis に XADD するだけ）。全コンポーネントが同一 EC2 に同居するため、ホストレベルの Security Group だけでは「Honeypot だけ外向きを塞ぐ」ことができない。そこで Security Group（ホスト全体の上限）と Docker ネットワーク分離（Honeypot コンテナ個別の遮断）の二層で設計する。

### 外向き通信の棚卸し（現状）

| 用途 | 通信先 | ポート | 現状の扱い |
|------|--------|--------|-----------|
| 名前解決 | DNS リゾルバ | TCP/UDP 53 | **常時許可**（apt/pull/SSH ホスト解決に必須） |
| 時刻同期 | NTP サーバー | UDP 123 | **常時許可**（ログのタイムスタンプ信頼性に必須） |
| OS / パッケージ / Docker イメージ更新 | apt・レジストリ等 | TCP 443 | **更新作業時のみ一時開放** |
| アラート通知 | Slack / Discord Webhook | TCP 443 | 未実装（Phase 3）。実装時に 443 を検討 |
| AI 攻撃分析 | OpenAI API 等 | TCP 443 | 未実装（Phase 4）。実装時に 443 を検討 |
| GeoIP 解決 | ローカル `.mmdb` 参照 | 外部通信なし | 実装済み・外部通信なし（アウトバウンド不要） |
| GeoIP DB 更新 | MaxMind | TCP 443 | `.mmdb` の手動更新時のみ（更新作業時に 443 を一時開放でカバー） |

### 第1層: Security Group アウトバウンド（現状の推奨）

デフォルトの全許可ルールを削除し、常時許可は DNS / NTP のみに絞る。

```
Outbound（常時）:
  - 53/udp      : 172.31.0.2/32          (DNS: AmazonProvidedDNS)
  - 53/tcp      : 172.31.0.2/32          (DNS over TCP フォールバック)
  - 123/udp     : 169.254.169.123/32     (NTP: Amazon Time Sync Service)

Outbound（更新作業時のみ一時追加し、作業後に削除）:
  - 443/tcp     : 0.0.0.0/0              (OS/パッケージ/イメージ更新)
```

- **DNS 宛先 `172.31.0.2/32`** はこの EC2 の実測値（`resolvectl status` の `Current DNS Server`）。VPC `172.31.0.0/16`（ap-southeast-2 デフォルト VPC）の `.2` = AmazonProvidedDNS。実際に DNS を扱うのはホストの `ens5` のみで、`docker0`・ブリッジ（コンテナ用）は DNS スコープを持たず、コンテナの名前解決もホスト経由でこの宛先に出るため、この 1 宛先で足りる。VPC CIDR が変わればこの値も変わる。
- NTP は Amazon Time Sync Service（リンクローカル `169.254.169.123`）に宛先を絞り、`0.0.0.0/0` を避ける。
- **443 は常時開けない。** 更新作業の直前に一時的に追加し、作業完了後にルールを削除する。これにより普段は HTTPS の外向きがゼロになり、侵害時の持ち出し・C2 経路を最小化できる。
- Security Group はステートフルなので、インバウンドで受けた攻撃接続の応答トラフィックはアウトバウンドルールに関係なく返せる。したがって Honeypot の応答のためにアウトバウンドを広げる必要はない。
- **Phase 3-4 への移行時**: 通知 / AI / GeoIP 更新の送信機能を実装したら、その送信を行う主体（Worker / API）向けに `443/tcp` の常時許可を追加する。可能なら宛先を既知エンドポイントに絞る（CDN で IP が変動する場合は NAT Gateway + ドメインフィルタや VPC エンドポイントを検討）。

### 適用手順（ロックアウト防止）

アウトバウンドを絞る作業は、DNS 宛先を誤ると名前解決が全停止し、原因が分かりにくい形で壊れる。以下の順で段階的に適用し、各段で動作確認する。

1. **DNS 宛先を実測で確定する**（推測で書かない）。
   ```bash
   resolvectl status   # Current DNS Server を確認（本環境は 172.31.0.2）
   ```
2. **常時許可ルール（53/123）を先に追加する**。この時点では既存の全許可（0.0.0.0/0）はまだ残す。
3. **動作確認する**。
   ```bash
   nslookup github.com   # 名前解決が通るか
   timedatectl           # 時刻同期（NTP）が効いているか
   docker ps             # コンテナが生きているか
   ```
4. **確認が取れてから全許可ルールを削除する**。追加→確認→削除の順にすることで、ロックアウトを避ける。
5. 不安なら DNS 宛先を一時的に VPC CIDR 広め（`172.31.0.0/16`）で許可し、動作確認後に `/32` へ狭める。
6. 管理 SSH（インバウンド）はアウトバウンド変更の影響を受けないため、万一おかしくなっても SSH で入り全許可へ戻せる。

> **コア機能はアウトバウンドを閉じても停止しない**（コードで確認済み）: 攻撃の受信・収集（インバウンド+ステートフル応答）、DB/Redis（内部通信 `127.0.0.1`）、GeoIP 解決（ローカル `.mmdb` 参照、外部通信なし）、分類・分析・API・Dashboard（ローカル/内部完結）。停止リスクが主にあるのは DNS 宛先の設定ミスのみ。

### 第2層: Docker レベルでの Honeypot 遮断（必須）

Security Group はホスト全体に効くため、「Honeypot コンテナだけ外向きゼロ」は Docker 側で実現する。

- Honeypot コンテナを **外部に出られないネットワーク**に接続する。`docker-compose.yml` で Honeypot 用ネットワークを `internal: true` にすると、そのネットワークはデフォルトゲートウェイを持たず外部へ出られない。

```yaml
networks:
  honeypot_net:
    internal: true   # 外部へのルートを持たない（受信は port mapping で可能）
  internal_net:
    internal: true
```

- Honeypot コンテナは `honeypot_net`（外向き不可）と、Redis への通信に必要な範囲のみに接続する。port mapping（`0.0.0.0:22->...`, `80/8080->...`）による**受信は internal ネットワークでも機能する**ため、攻撃トラフィックの観測には影響しない。
- これにより、万一 Honeypot プロセスが掌握されても、コンテナからインターネットへ出て行く経路（C2 接続・外部スキャン・データ持ち出し）が存在しない。

### 外向き通信をコンポーネント別に見た許可方針

| コンポーネント | 外向きの必要性（現状） | 方針 |
|---------------|----------------|------|
| Honeypot | なし | Docker `internal: true` で外部遮断 |
| Event Worker | なし（通知/AI/GeoIP は未実装） | 外部遮断。Phase 3-4 実装時に 443 を許可 |
| API | なし（通知/AI は未実装） | 外部遮断。Phase 3-4 実装時に 443 を許可 |
| Dashboard | なし（API 経由） | 外部遮断 |
| PostgreSQL | なし | 外部遮断（内部のみ） |
| Redis | なし | 外部遮断（内部のみ） |
| ホスト | DNS/NTP のみ常時、更新時に 443 | 53/123 を常時許可、443 は更新作業時のみ一時開放 |

### 設計判断の根拠

- **全許可をやめる理由**: Honeypot は侵害を前提とする資産。侵害時に外向きが全開放だと、踏み台化・外部攻撃の中継・ログ持ち出しが素通りする。これは product steering の「隔離」「最小権限」「ネットワーク分離」方針に反する。
- **ほぼ全閉じにできる理由**: アプリ本体に外部送信機能が未実装（通知・AI・GeoIP はいずれも Phase 3-4）であり、現状「アプリ用途の正当な外向き通信」が存在しない。したがって常時許可は DNS/NTP のみで足り、HTTPS すら常時開ける必要がない。
- **443 を常時開けない理由**: 現状 443 の恒常的な用途は無く、必要なのは OS/イメージ更新作業時だけ。普段ゼロ・作業時のみ一時開放にすることで、侵害時の持ち出し・C2 経路を最小化する。
- **DNS/NTP だけ残す理由**: 名前解決が無いと apt/pull/ホスト解決が動かず運用不能になり、時刻同期はログのタイムスタンプ信頼性（Honeypot の生命線）に直結するため、常時許可とする。
- **二層にする理由**: 同一ホスト同居構成では SG だけでは Honeypot を個別に遮断できないため、Docker の `internal` ネットワークで Honeypot の外向きをゼロにする。SG は運用通信の上限として機能させる。
- **Phase 3-4 への移行**: 通知/AI/GeoIP 更新を実装したら、その送信主体向けに 443 の常時許可を追加する（宛先はできるだけ絞る）。
- **スコープ外**: pg_dump 等の管理データ取得は管理 SSH（インバウンド）で完結し、アウトバウンド設計の対象外。

## データ保護

### パスワードの取り扱い

攻撃者が試行したパスワードは**平文で保存**します。

```python
# 平文のまま記録（分析用途を優先）
ssh_data = SSHEventData(
    username=username,
    password=password,  # 平文
    ...
)
```

**判断根拠:**
- 辞書攻撃で使われるパスワードの傾向分析（Top パスワードランキング等）に平文が必要
- 攻撃者が使う辞書ファイルの特定に利用
- 先行 Honeypot プロジェクト（Cowrie, Kippo）は平文記録が標準

**リスク認識:**
- DB が漏洩した場合、パスワードリストとして悪用される可能性がある
- 攻撃者が誤って自身のパスワードを入力するケースがある

**対策:**
- DB は外部非公開（127.0.0.1 のみ）
- Dashboard / API は認証必須
- 本番環境では DB バックアップを暗号化
- 将来的に一定期間後のマスク処理を検討

### IP アドレスの取り扱い

IP アドレスは攻撃分析に不可欠なためそのまま保存しますが:
- Dashboard へのアクセスは認証必須
- DB は外部非公開
- 将来的に一定期間後の匿名化（上位ビットのマスク）を検討

## 認証

### API (Phase 1)

- HTTP Basic Auth（`Authorization: Basic <base64>` ヘッダー）
- タイミング攻撃対策: `secrets.compare_digest` を使用
- サーバー側の認証情報は環境変数で設定（ハードコードしない）

### フロントエンドの認証情報

- Dashboard はログインフォームで認証情報を入力させる
- 認証情報はソースコードに埋め込まない（ハードコード禁止）
- 入力値は base64 エンコードして localStorage に保持し、API 呼び出し時に付与する
- API が 401 を返した場合は認証情報を破棄してログイン画面に戻す

### Phase 2 以降の計画

- JWT トークンベース認証に移行予定
- ログイン試行回数制限（Rate Limiting）
- セッション管理

## コンテナセキュリティ

| 対策 | 実装 |
|------|------|
| 非 root 実行 | Dockerfile で `USER honeywatch` |
| 軽量ベースイメージ | `python:3.12-slim`（攻撃面を最小化） |
| 不要パッケージ排除 | `--no-install-recommends` |
| restart policy | `unless-stopped`（クラッシュ時自動復旧） |
| read-only FS | 将来的に `read_only: true` を検討 |

## 既知のリスクと今後の対策

### ホスト侵害時のコンテナ隔離の限界

現在の構成では全コンポーネントが同一 EC2 上の Docker コンテナとして動作しています。Docker のプロセス隔離はネットワーク・ファイルシステムレベルの分離を提供しますが、**ホスト自体が root 権限で侵害された場合は全コンテナにアクセス可能**です。

**リスクシナリオ:**
- Honeypot のライブラリ（asyncssh, aiohttp）にリモートコード実行の脆弱性が発見される
- 攻撃者がコンテナ内で任意コードを実行 → コンテナエスケープ → ホスト権限取得
- DB 内の全ログデータ・API 認証情報が漏洩

**現時点で対策しない理由:**
- asyncssh / aiohttp でコンテナエスケープまで到達するには高度なエクスプロイトチェーンが必要
- Honeypot はユーザー入力を受けるだけで、任意コード実行の攻撃面が小さい
- EC2 2台 + VPC 分離の構成はコストが倍になり、個人プロジェクトの規模に見合わない

**本番環境で対策する場合:**
- Honeypot を別 EC2（別 VPC サブネット）に配置し、Redis のみ VPC Peering で接続
- Honeypot EC2 には DB / API へのネットワーク経路を一切持たせない
- ログ保管用 EC2 は Private Subnet に配置し、インターネットから直接到達不可にする
- Honeypot EC2 は定期的に破棄・再作成する（Immutable Infrastructure）
